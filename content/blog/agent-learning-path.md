我有一套自己的知识管理方式：把学到的内容整理进一个由 LLM 维护的 Wiki。而 Agent 本身就是我一直在学、也在用的东西。这篇聊聊我走过的路径，以及每个阶段真正的分水岭。

## Stage 1-2：别跳过基础

跨 Provider 调用、错误处理、重试、流式输出。这一步很枯燥，但它是所有后续的底盘。我见过很多直接跳到「搭 Agent」的人，最后都在 Prompt 工程和 Token 管理上补课。

## Stage 3：Tool Calling 才是核心

Agent 之所以是 Agent，不是因为它「聪明」，而是因为它**能调用工具**。ReAct（Reasoning + Acting）是经典控制流：模型推理 → 决定动作 → 调用工具 → 观察结果 → 再推理。

这里有个容易被低估的东西：**工具 Schema 设计**。给模型的工具描述，决定了模型能不能选对、用对工具。描述含糊，模型就瞎猜；描述过长，Token 成本飙升。

## Stage 4：从单 Agent 到多 Agent

单个 Agent 有明确天花板：上下文有限、容易偏离、一次失败全盘皆输。多 Agent 不是「更多模型」，而是**角色分离**：

- 编排者负责拆任务、分派、汇总
- 执行者各自专注一个子领域
- 交叉验证、对抗审查降低单模型的偏见

我学到的最重要一课：多 Agent 系统的复杂度不在模型，在**协作拓扑和失败处理**。谁负责纠错？一个 Agent 挂了对不对整体重跑？

## Stage 5-6：记忆与 RAG

短期记忆是上下文窗口，长期记忆是向量库。RAG 把「模型不知道的」变成「模型能查到的」。但 RAG 的坑很深（我单独写了一篇）。

## Stage 7：评估与可观测性

不做评估的 Agent 项目，等于在裸奔。延迟、Token、追踪、错误率——这四个指标没有，你连「它今天变好了还是变坏了」都不知道。

## 一句话总结

学 Agent 不是学框架，是学**控制流、工具设计和系统思维**。框架会过时，这三样不会。
