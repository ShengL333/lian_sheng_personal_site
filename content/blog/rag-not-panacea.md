最近一年我一直在做一件事：让 LLM 帮我维护一个个人知识 Wiki。文档进 raw 目录，AI 负责消化成结构化笔记、维护索引、处理交叉引用。理想很美好，落地全是 RAG 的细节。RAG 不是接上就能用的万能药，它是一台需要反复调校的机器。

## 1. 分块策略决定了检索上限

固定 500 token 切一刀？还是按标题/段落切？这两种方案的检索质量天差地别。固定长度切块，语义边界被切断；按结构切，每块语义完整但大小不一。没有万能药，只有取舍——我最后用「标题感知」的分块，配合过长的块再切。

## 2. 检索质量 > 生成质量

用户感知到的 RAG 体验，80% 取决于检索回了什么。模型再强，检索回一堆无关片段，回答就是幻觉。我学到的调试方法：先把检索结果裸展示，看相关性，再谈生成。

## 3. Embedding 模型是地基

换了更好的 embedding 模型，效果提升是立竿见影的。这个钱值得花，比反复调 Prompt 有效得多。

## 4. 混合检索 > 纯向量

向量检索对「语义近似」强，对「关键词精确匹配」弱。产品名、代码标识符、专有名词——这些恰恰是向量容易丢的。BM25 关键词检索 + 向量检索混合，再做个简单重排，比任何单一路径都稳。

## 5. 没有评估 = 盲人摸象

每次改分块策略或检索逻辑，我怎么知道是变好了？给一组固定的测试问题，标注期望答案，跑一遍算命中率。这就是 LLM 领域的「pytest」——没有它，所有「感觉更好了」都是错觉。

## 一句话总结

RAG 不是一个组件，是一条需要**分层调试**的管线：分块 → 嵌入 → 检索 → 重排 → 生成 → 评估。每一层都有独立的坑。它解决的是「让 LLM 读到相关文档」这个检索问题，不是「让 LLM 有知识」这个积累问题——指望一个 RAG 管线包治百病，就是拿螺丝刀当扳手使。
