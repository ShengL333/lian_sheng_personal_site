单 Agent 的能力边界很清楚：一个模型、一个上下文、一条推理链。当任务复杂到单个 Agent 处理不了时，很自然的想法是「再多放几个 Agent」。但多 Agent 不是人多力量大，**没有设计的分工只是一群模型在抢上下文**。

## 角色分离：每个 Agent 只干一件事

编排者、研究员、执行者、审查者——每个角色有明确的职责边界和独立的上下文。好处是：

- 上下文不打架，每个 Agent 只看到自己需要的
- 可以针对每个角色选不同模型（贵的用在高价值环节）
- 单个 Agent 失败可以局部重试，不用整体重跑

## 交叉验证：让答案经得起推敲

单个模型生成的内容，它自己检查往往发现不了问题——「自己审自己的作业」会惯性认可。多 Agent 的经典用法是让一个独立的审查 Agent 去挑错，或者让两个 Agent 各自独立做一遍再比对。对抗式审查能显著降低单模型的系统性偏见。

## 失败处理：拓扑比数量重要

一个常见的反模式：A 调用 B，B 失败，整个流程回到原点重跑，Token 烧掉一轮又一轮。多 Agent 系统里，「谁负责纠错、失败后降级到哪一步」必须提前设计。我倾向用图结构的工作流（Graph + HITL），把分支和人工检查点显式画出来，而不是让 Agent 自己即兴编排。

## 评估：Agent 团队也要有 KPI

每个角色的输出质量都要独立评估。编排者的分派是否合理？研究员的检索是否命中？审查者有没有漏掉真问题？逐角色建评估集，才能定位到「是哪一环在拖后腿」。

## 一句话总结

多智能体系统的复杂度不在模型数量，在**角色划分、协作拓扑和失败恢复**。想清楚这三个，再加人（模型）才有意义。
